## 目的と初期範囲

NIHOkamakuraでは日本語原稿から英語版を、NIHO experienceでは英語原稿から日本語版を作る。読者はサイト内のどのページでも「日本語 / English」を切り替えられ、管理者は同じ編集画面で各言語の実際の見た目を確認・編集できる。

初期版から **ja→en、en→jaの両方向**を扱う。ただし翻訳の基準となる原文言語はサイトごとに1つで、訳文を手直ししても原文への逆翻訳は行わない。

「サイト全体」の対象は、公開ページ本文、ヘッダー、ナビゲーション、フッター、共通部品、画像説明、公開メタ情報、およびサイト内で描画する登録済み業務ブロックの表示文言。画像に焼き込まれた文字は、言語別画像への手動差し替えで扱う。外部予約サイト等へ遷移した後の画面は、そのサービスの言語対応に従う。

成功条件は、各サイトの公開ページ間を日英どちらでも巡回でき、未翻訳のメニューや別言語への意図しない戻りがなく、原文更新・翻訳失敗によって公開中のサイトが壊れないこと。

## 現状と組み込み位置

### niho-web

調査時の `origin/main` は `0447ea1`（プロジェクト一覧・ダッシュボード #35）。

- `src/types.ts` の `PageDocument` は既に `siteId / pageId / locale / revision` を持つ。
- `src/editor-types.ts` の `EditorTarget` も `siteId / pageId / locale`。下書き保存のversion比較、公開前差分、確認token、公開履歴がある。
- `src/pages.ts` はlocaleを考慮したパス重複確認と、canonical / robots / OG等の公開メタ情報を扱う。
- `src/components.ts` と `src/component-expand.ts` は共通部品と展開を扱う。`src/editor-rich-text.ts` はリッチテキスト編集、`src/assets.ts` は素材参照を扱う。
- 現時点では、日英のページ対応、翻訳単位、翻訳の更新状態、言語切り替え、言語別の公開ルート、翻訳ジョブの契約はない。`locale` があるだけではサイト全体を多言語化できない。
- 認証・DB・AI認証情報・翻訳ジョブ・公開インフラは、既存方針どおり認証済みホストの責務。

### niho-appの既存自動翻訳

参考実装：

- `apps/api/src/ops/content-translation.ts`：原文のhash、非同期処理、最新原文の再取得、冪等性、公開可否、失敗時の扱い。
- `apps/api/src/ops/vertex-translate-client.ts`：Vertex認証・呼出し、出力中断の検出、本文を含めないエラー処理。現行の公開関数は日本語→英語を前提とする。
- `apps/api/src/ops/content-translation-structured.ts` / `content-translation-markdown.ts`：構造を壊さず本文の葉を取り出す方式、URL等の保護。
- `specs/initiatives/public-entrance-auto-translation.md`：現在の公開拠点ページの方針。**英訳は自動生成・手編集不可**で、古い翻訳は出さず原文へ戻す。
- `docs/design/content-auto-translation-v1.md`：過去の手動訳保護も記載されているが、上記の最新仕様で手動編集は廃止されている。履歴の記述を現行仕様と取り違えない。

再利用するのは翻訳エンジン・認証・非同期処理・変更検知の仕組み。今回必要な「訳文の手編集」「承認」「日英別の公開版保持」は追加する。既存の拠点公開ページの自動翻訳方針は変更しない。

翻訳・用語集・候補・公開版は制作Siteに所属させ、既存 `ContentTranslation` のspot所属へ格納しない。初期2サイトは既存 `NihoWebPage` と同じNIHO法人所有の事業コンテンツであり、拠点や編集者個人の削除には連動しない。APIとworkerは許可済みSiteと現在のスタッフ権限を検証する。ライブラリのProjectは制作上の論理的なまとまりで、存在しないDBのProject／会員権限を前提にしない。ホスト実装時には `specs/policies/data-ownership.md` にこの所属とサイト廃止時の保持・公開停止を追記する。

## 読む人と編集する人の操作

### 読者

1. 通常のURLでサイトを開く。鎌倉は日本語、Experienceは英語で始まる。
2. PCではヘッダー右上、スマホでも見つけやすいヘッダー／メニュー内にある「日本語 / English」を選ぶ。国旗だけの表示にはしない。
3. **現在のページに対応する他言語版**へ移動する。料金ページなら料金ページのまま切り替わる。
4. メニュー・カード・フッターから移動しても、選んだ言語を保つ。
5. URLを共有すると、相手にもその言語のページが開く。

URLを言語の正とする。ブラウザ言語や居住国による強制転送は初期版で行わない。必要なら「View in English」の案内を出せるが、表示言語自体はURLで決める。国籍と使用言語を同一視しない。

### 初回設定

1. サイト設定の「言語」で原文言語を確認する。鎌倉＝日本語、Experience＝English。
2. 追加言語を有効にして「サイト全体を翻訳」。既存ページ・共通部品・SEO文言の翻訳下書きを非同期作成する。
3. ページ一覧で「未翻訳 / 翻訳中 / 要確認 / 確認済み / 更新あり / 失敗」を確認する。
4. エディター上部を「日本語 / English」で切り替え、PC・スマホの見た目を確認する。原文との比較を開き、文章や画像を直せる。
5. 全公開ページと共通部品の準備が揃ったら、その言語を初めて公開する。同時に言語切り替えリンクを公開サイトへ出す。

### 日常の更新

1. 原文の編集を保存する。保存を翻訳完了まで待たせない。
2. 変更された文章だけを翻訳し、新しい候補を作る。
3. 原文は先に公開できる。翻訳側の公開サイトは、前回承認した完成版をそのまま表示する。
4. 管理画面には「英語：原文の更新あり」等と変更箇所数を表示する。読者向けのページへ内部状態を出さない。
5. 翻訳側で「旧原文 / 新原文 / 現在の訳 / 新しい翻訳案」を確認し、採用・手修正・現在の訳を維持して確認済みにする、のいずれかを選ぶ。
6. 翻訳の公開前確認で対象ページ・共通部品・URLを見て、その言語を公開する。

自動翻訳済みの文章も、手修正した文章も、生成処理が現在の編集内容を上書きしない。再翻訳は常に別の候補として扱う。手修正した訳文を無言で元に戻さない。

### 管理画面の配置

- サイト設定：原文言語、追加言語、公開状態、用語集。
- エディター上部：現在の表示言語、原文／翻訳の区別、その言語の確認・公開状態。アプリ自体のUI言語設定とは別にする。
- ページ一覧：ページは1行。日英それぞれの状態を並べる。同じページを独立した2ページとして一覧へ増殖させない。
- キャンバス：選択言語の実際の文書を描画。訳文でも同じ位置から文章・画像を編集できる。
- 右パネル：選択項目の原文、訳文、更新箇所、新しい翻訳案。「変更箇所だけ」を巡回できる。
- 翻訳言語の編集では文章・画像・表示用リンク先を操作する。構造・配置を変える操作は「共通デザインの編集」へ切り替え、両言語に影響することを示す。
- 保存前の言語切り替え・別ページ遷移では入力を保持し、競合時に自動で上書きしない。

## 方式の比較

| 方式 | 編集・運用 | SEO・公開 | 判断 |
| --- | --- | --- | --- |
| 閲覧時に翻訳スクリプトで表示を置換 | 導入は小さい。見た目確認、手修正、変更追従の管理が難しい | 表示待ちや原文のちらつき、URLと本文の不一致を避ける設計が必要 | 今回の主方式には採用しない |
| 日英ページ／サイトを独立コピー | 各言語を自由に変更できる | 言語別URLは作れるが、構成・リンク・画像の二重保守になる | 将来、独立デザインが必要になった場合の選択肢 |
| **共通構造＋言語別コンテンツを保存して公開文書を生成** | 構成は一元管理。訳文・画像を調整できる。更新箇所を追跡できる | 完成済みHTMLを言語別URLで公開し、承認済みの版を維持できる | **推奨** |

## 推奨する内部設計

### 1. サイト・ページ・言語の関係

- Siteは `sourceLocale`、`defaultLocale`、`enabledLocales`、言語別公開状態を持つ。初期設定ではdefault＝sourceとするが、翻訳方向とURLの既定言語は概念を分ける。
- 原文言語の変更は通常の切り替え操作にしない。公開後に変える場合は、URL・翻訳基準・既存訳を扱う移行操作が必要。
- 同じページの日英は同一の論理 `pageId` を持つ。別の `pageId` を自動採番してコピーする方式を避ける。
- 実際の表示文書は現在の契約に合わせ、`siteId / pageId / locale / revision` で識別する。
- `ja-JP` 等の文書localeと、URL用の言語キー `ja / en` の対応を明示する。既存文書のlocaleを黙って置換しない。

### 2. 共通部分と言語別の差分

| 共通で管理するもの | 言語別に持つもの |
| --- | --- |
| ページ構成、ノード、セクション順、レイアウト、共通スタイル、レスポンシブ設定 | 見出し・本文・ボタン・メニューの文言、alt・caption・aria-label等 |
| 論理ページID、内部リンクの宛先、商品・予約等の実体ID | SEO title・description、OG表示文言、画像参照、必要な外部リンク差し替え |
| 通貨、実際の金額・日時・場所、取引ルール | 言語に応じた表示formatter、表示用の説明 |

画像は元の素材参照を共用し、必要な箇所だけ別素材へ上書きする。画像ファイルを翻訳のたびに複製しない。権利・出所・公開可否は既存の素材契約を維持する。

実サイトに既にある`img.attrs.src`も、`AssetReference`へ一括移行せず同じ`node.<id>.asset`翻訳単位で扱う。言語別overrideはasset参照または厳格に検証したURL source（`src`＋任意の単一URL `srcset`）で、片方を選ぶともう片方を原子的に外す。OG画像sourceも手動専用の任意unitにする。URLの安全性検証はホストの素材承認を代替せず、公開可否と権利確認はホストが担う。

英語の文字量でレイアウトが崩れないよう、共通デザインを自動高・折り返し前提にする。言語別の独立レイアウトは初期範囲に加えず、まず訳文の調整と共通レイアウトで解決する。

### 3. 翻訳単位と変更検知

概念上の保存形：

```text
SiteLocalizationConfig
  siteId, sourceLocale, defaultLocale, enabledLocales, glossaryVersion

LocalizationUnit
  siteId, scope(page / shared-component / template / CMS-record), ownerId
  unitId, fieldKind, sourceLocale, sourceValue, sourceFingerprint

LocalizedValue
  unitId, targetLocale, draftValue, editOrigin(AUTO / MANUAL)
  reviewedSourceFingerprint, version

TranslationCandidate
  unitId, targetLocale, sourceFingerprint, proposedValue
  contextVersion, glossaryVersion, engineVersion, status

LocalizedRelease
  siteId, locale, releaseId
  page snapshots + localized shared-component snapshots + route/SEO manifest
```

これは論理モデルであり、テーブル名や物理分割はホストの保存契約に合わせる。Project/Siteの所有関係を必須にする。

- DOMの配列番号や表示文字列をIDにしない。既存の安定したelement ID＋fieldを基本キーにする。現在のTextNodeにはIDがないため、`children[2]` のような位置へ訳を結び付けない。
- リッチテキストは文章の意味が通る段落単位で翻訳する。強調やリンクで分かれた短いTextNodeを別々に翻訳すると語順が崩れる。段落の安定IDと、安全なinline構造・リンク参照を持つ翻訳単位を追加する。
- 安定IDがない直接のテキスト等は、移行時に一度だけID付きの編集単位へ正規化する。保存形式を拡張する場合は、旧schemaの読込・新形式への移行・旧クライアントからの編集拒否を明示する。
- 部品は定義の文章を一度翻訳する。インスタンス固有の文言だけを別単位にし、全ページで同じヘッダーを重複翻訳しない。
- 原文fingerprintには本文だけでなく、翻訳方向・文脈・用語集・指示の版を含める。無関係な見た目の変更だけでは再翻訳しない。
- 原文の削除・段落分割・部品差し替えでは対応を再評価する。消えたIDの訳を別のIDへ自動移植しない。
- 翻訳言語側の画像や外部リンクを手修正した後、対応する原文側が変わったときも「要確認」にする。上書きはしない。

### 4. 翻訳実行

保存 → 変更単位の抽出 → 非同期ジョブ → 翻訳候補 → 管理者確認 → 言語別公開、の順とする。

- 保存後に短時間のまとめ処理を入れ、連続入力を一回の翻訳へまとめる。変更した単位だけを対象にし、閲覧時のAI呼出しは行わない。
- niho-appホストでは既存のCloud Tasks / Vertex認証と呼出し基盤を利用する。共有する翻訳クライアントにsourceLocale / targetLocale / contentKind / glossaryを渡せる設計へ拡張し、既存の日本語→英語関数は互換wrapperとして残す。
- `ContentTranslation` のスポット固有loaderや公開ページ用ゲートを、そのまま制作プロジェクトへ適用しない。未公開原稿も扱える専用のProject認可とジョブ契約を用意する。
- ワーカーは保存済みの原文と現在権限を読み直す。完了時も原文fingerprint・候補version・手編集versionを比較し、古い結果を現在の訳文へ採用しない。
- 金額・日付・住所・予約ID・URL・電話番号等は、構造化値／保護参照として維持する。AIに文書のHTML、任意の実行コード、リンク先の変更権限を渡さない。
- 出力は元の単位IDと許可された本文形式で検証する。空出力、途中終了、参照欠落、構造の増減は候補として受理しない。
- 翻訳失敗は下書き側へ記録して再試行できるようにする。原文保存・既存公開版は成功状態を保つ。
- 本文をログへ出さない。サイト単位の使用量・失敗件数・再試行を観測し、重複実行と全件再翻訳を抑える。

用語集はサイト単位。NIHO / NIHOkamakura / NIHO experience等の表記と、翻訳せず残す語を指定できる。日本語の説明文と英語の短いUIラベルに同じ文体を強制せず、本文・見出し・ボタン等の文脈を渡す。

### 5. リンク、URL、SEO

| サイト | 既存の原文URL | 追加言語URL |
| --- | --- | --- |
| NIHOkamakura（日本語原文） | `https://kamakura.niho.life/catering` | `https://kamakura.niho.life/en/catering` |
| NIHO experience（英語原文） | `〈Experienceの公開origin〉/help` | `〈Experienceの公開origin〉/ja/help` |

上記は既存ルートに沿った設計例。既存URLの末尾スラッシュ有無をそのまま保ち、移行時に実際の公開ルートと照合する。鎌倉の新サイト確認用originを本番originと同一視しない。

- 原文URLを保ち、追加言語に `/en/` または `/ja/` を付ける。初期版のslugは言語間で共通とし、自動翻訳しない。
- `/en`・`/ja` と既存ページパス／テンプレートパスの衝突を初回設定で検出する。
- 内部リンクは可能な限り `pageId`＋anchor等の意味参照から、現在言語の公開URLへ解決する。既存の文字列hrefは移行時に同サイトのルートへ対応付け、外部URLを誤変換しない。
- 言語切り替えリンクは、同じpageIdの**公開済み**対応URLを使用する。初回の翻訳が未公開なら、その言語へのリンクを出さない。トップへ黙って飛ばさない。
- 言語別のHTMLをSSRまたは静的生成し、本文・ナビ・`html lang`・OG等を同じ公開版から描画する。
- canonicalは各言語の自分自身を指す。英語ページのcanonicalを日本語へ向けない。公開済み対応ページには相互の `hreflang` とself、原文側に対応する `x-default` を生成する。
- sitemapは公開済みURLだけを含める。preview・翻訳下書きはnoindexとし、公開ルートやhreflangへ混ぜない。
- URL／localeをCDNとサーバーのキャッシュキーに含める。同じURLをcookie次第で異なる言語本文に変えない。

### 6. 公開・ロールバック

- 編集中の構成・デザインは共通だが、**公開版は言語ごとに完成したsnapshot**を持つ。原文だけ更新した場合、訳文側は文章だけでなく、前回の構成・共通部品・ナビも含めて維持する。
- 翻訳の公開は、ページ、使用する共通部品、内部リンク、ルート、メタ情報を同じrelease manifestで原子的に切り替える。本文だけ新しくなり、メニューが旧版のままになる公開を避ける。
- 新しい言語の初回公開では、対象の公開ページと共通部品を全件確認する。「サイト全体を英語」と表示しながら、未翻訳箇所を原文で埋める公開はしない。
- 追加ページは原文で先に公開できる。翻訳側には以前のナビ・ページ集合を維持し、その新ページの対応URLは翻訳公開まで作らない。
- ページ削除・非公開化は、対応する全言語への影響を確認する。内容の取り下げや公開権限喪失は、翻訳側にも即時反映する。古い公開snapshotを保持することを理由に非公開内容を残さない。
- 確認tokenにはsite / locale / 原文版 / 訳文版 / 共通部品版 / 公開ルートmanifestを結び付ける。途中の更新はconflictとして再確認する。
- 公開取消・ロールバックも言語別に実行できるが、対応ルート・ナビ・SEOを含むsnapshot単位とする。失敗時は現在のreleaseを保つ。

### 7. 動的データ・業務ブロック

- block registryは翻訳可能な表示propsと、その言語での描画対応を宣言する。すべてのstring propを一律にAIへ渡さない。
- CMS連動ページは同じレコードの言語別内容へ対応付ける。テンプレート翻訳だけでCMS本文まで翻訳済みとは扱わない。
- 商品・体験・予約枠・フォーム送信・決済の実体とIDは共通。説明・入力補助・エラー表示だけをlocaleへ合わせる。翻訳ごとに商品や予約在庫を複製しない。
- niho-appに既存訳がある業務データは、そのデータの所有者が提供する言語別read modelを利用する。サイト側へ二重の原稿正本を作らない。
- 業務側が正本の公開テキストを仮想ページで見せる場合、原文snapshotだけをdocument-levelの読み取り専用にし、理由と既存の正本編集routeを表示する。コピーした書込可能な原文を作らず、派生言語snapshotはホストが明示的に読み取り専用としない限り編集できる。
- 未対応blockや未翻訳CMSレコードは、初回の追加言語公開チェックで箇所を特定する。翻訳が必要な本文を黙って原文表示にして合格扱いしない。

### 8. niho-webとホストの分担

| niho-webの公開パッケージ | 認証済みホスト・公開基盤 |
| --- | --- |
| 言語設定・翻訳単位・候補・状態の型と検証 | Project membership、編集・公開権限、全処理の認可 |
| 共通文書＋言語別差分の解決、内部リンク解決 | 永続化、楽観ロック、ジョブ、AI認証情報・呼出し |
| エディターの言語切り替え、文章・画像編集、比較・確認UI | 翻訳実行、上限、監査、削除連動 |
| 公開文書とSEO manifestの生成契約 | origin・ルーティング・CDN・公開snapshotの原子的切り替え |

既存EditorAdapterに無理に任意fieldを増やすより、optionalなLocalizationAdapterと、サイト／言語単位の公開prepare・apply契約を加える。未対応ホストは単言語の既存編集を継続できる。

GA4／Search Consoleは同一サイトの言語別パスとして扱える。多言語化だけを理由に測定IDやプロパティを増やさず、二重タグを入れない。分析UIで言語別に見る場合は公開routeとlocaleの対応を利用する。既存の接続契約PR #33とは別の設計・実装にする。

## 受入シナリオ

1. 鎌倉の日本語原稿から英語下書き、Experienceの英語原稿から日本語下書きを作成できる。
2. 同じ料金ページで言語切り替えし、メニュー・共通部品・画像説明・SEOを含む対応言語のページを開ける。
3. 翻訳文と画像の手修正は原文や他言語に影響しない。共通デザインの変更は両言語の下書きへ反映される。
4. 段落内に強調・リンク・改行がある文章も、意味と参照を維持する。段落の移動で別の訳が混入しない。
5. 原文を先に公開しても、翻訳側の前回公開版を維持する。確認済み訳を公開したときにだけ切り替わる。
6. 原文の新旧と現在の訳・新候補を比較できる。手修正中に完了した古いjobが入力を上書きしない。
7. 翻訳失敗・quota・並行編集・再試行でも原文保存と公開中ページを保つ。再試行で重複候補や重複公開を作らない。
8. 別Project・別Siteの原稿、翻訳、候補、素材、公開tokenを読取／書込できない。
9. 新言語の初回公開前に、未対応block・未翻訳ページ・リンク切れを検出する。下書きがsitemap等へ出ない。
10. 各言語の本文とhtml lang・canonical・hreflang・OGが同じ公開版に揃う。CDNに別言語の本文が混入しない。
11. 新規ページ・削除・非公開化・ロールバックで、ナビと両言語の対応URLを整合させる。
12. PCと320pxを含むスマホで、日本語長文と英語の文字量、キーボード操作、選択言語の識別を確認する。

## 決定事項と実装時の確認

オーナーへの主要な3問は冒頭のとおり回答済み。追加回答がなくても、この設計を実装計画へ落とし込める。

実装着手時に実サイトを調べて確定する事項：

- 現在のページ・テンプレート・CMS・外部埋込の棚卸しと、言語別に差し替える画像の有無。
- Experienceの正式な公開originと既存の日本語URL／訳文の有無。既存訳があれば対応付けて取り込み、再翻訳で上書きしない。
- 初期の固有名詞・用語集。「街のリビング」等の表現は既存サイトの承認済み英語を優先する。
- 部品・テンプレートを含む公開単位と、ホスト側のsite全体release契約の具体化。

## 実装順

1. **言語・文書・ルート契約**：翻訳単位の安定ID、共通文書＋言語別差分、日英ページ対応、旧文書の移行、locale別URL解決をniho-webに追加。
2. **ホスト翻訳基盤**：Project/Site所属の保存と権限、ja↔enの翻訳クライアント、非同期ジョブ、候補・原文変更検知・競合保護を実装。niho-app側の変更は既定方針どおりDraft PR。
3. **編集画面**：言語切り替え、キャンバス・文章・画像編集、変更比較、確認状態、サイト全体の翻訳一覧を追加。
4. **公開とSEO**：言語別snapshot・共通部品・ルート・SEOの原子的公開、言語切り替えリンク、初回全体チェック、取消・ロールバック。
5. **2サイトで受入**：鎌倉ja→en、Experience en→jaの両方で公開導線と原文更新を確認してから段階展開。

大きい一括PRにせず、上記の依存順で契約・ホスト・編集・公開を分ける。設計合意前のproduction code変更や、既存サイトへの公開設定変更はこの設計作業に含めない。
