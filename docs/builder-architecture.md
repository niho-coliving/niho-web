# 汎用サイトビルダーの設計

## 目的と制作体験

NIHO Webは、テキスト・画像・ボックス・再利用コンポーネントを配置し、レイヤーで階層を整理し、幅ごとのレイアウトと状態・動きを定義する共通の制作基盤とする。鎌倉とExperienceは同じ基盤を利用する接続事例である。coreとeditorはサイト名、予約・決済、CMSの業務上の意味を知らない。

制作担当者の基本操作は、挿入 → レイヤーの選択・階層整理 → 配置・見た目・動きの編集 → プレビュー → 下書き保存 → 公開前の確認 → 公開である。操作する入口がパレット、キャンバス、レイヤー、キーボードのいずれでも、同じ文書操作と検証へ接続する。

編集画面全体のUI/UXはSTUDIOのデザインエディタを再現することを目標とする。確認できる公式画面の構成、名称、アイコン、余白、入力、選択状態を基準にする。制作定義の汎用性を説明するための独自メニューは増やさず、モーションは通常/条件付きスタイル、変形、アニメーションの直接設定から扱う。説明的な動きのプリセットを標準画面へ並べない。

## 責務と正本

| 層 | 正本と責務 | 持ち込まないもの |
| --- | --- | --- |
| 文書・描画core | PageDocument、ノードID、構造・スタイル検証、CSSとReact/HTML描画 | サイト名による分岐、認証、外部通信 |
| 制作定義 | 挿入する部分木、初期レイアウト、モーションの宣言、表示用の説明 | 保存済み文書から実行するJS、任意CSS、秘密 |
| 編集操作 | 構造・値・スタイルの変更、locks、undo/redo、保存済み基準 | DOMのHTMLを無検証で正本にすること |
| レイヤー | ノードIDを基準にした階層投影・選択・折りたたみ | 別のレイヤー文書、配列位置を永続IDとして使うこと |
| 編集セッション | 対象と版、読込・競合・未保存・復旧、機能の可用性 | 任意機能の障害を文書全体の障害と混同すること |
| キャンバス | 実際のページ幅、表示倍率、選択・編集の操作 | 表示倍率をページ幅や保存styleへ書き戻すこと |
| host integration | 認証・認可、保存・公開、データ取得、業務block、素材解決 | UI上の選択だけに依存した認可 |

PageDocumentと共通部品ライブラリが制作内容の正本である。制作定義はこれらを作るための道具であり、プリセットの名前を公開rendererが解釈し直す設計にしない。定義の変更後も、既に作成したページの表示は保存済みの文書に従う。

## 挿入とコンポーネント

通常要素、構成済みの部分木、再利用部品のinstance、業務blockを区別する。

- 通常要素はテキスト・画像・boxなどの検証済みノードとして保存する。
- 構成済みの部分木はカード・横並び・Grid等を組み立てる初期値であり、挿入後は通常要素として自由に編集する。挿入ごとに全ノードIDを採番する。
- 再利用部品のinstanceは部品の正本を参照し、公開したpropsと外枠の見た目を変更する。部品の編集とページ上のinstance編集を区別する。
- 業務blockはhostの登録契約に従う。価格・在庫・送信先・予約可否などを見た目のpropsと混ぜない。安全なプレビューと公開時の業務処理を分ける。

構成済み部分木に業務blockを含めても、hostの配置許可を迂回できない。配置前と文書操作後の両方で、未登録block、許可外props、重複ID、不正な入れ子、深さとノード数、locksを検証する。

## レイヤーと選択

レイヤーは文書の投影であり、順序と親子関係を別ストアに複製しない。ノードIDを編集対象の識別子とし、現在の文書からpathを引き直す。兄弟の挿入・移動・削除で配列位置が変わっても、同じIDの選択を保つ。対象が削除されたときは、隣の要素を誤って編集せず選択を解除する。

テキストの内容と、テキストを持つ要素を区別する。共通部品の展開ノードには編集元への対応を保ち、ページ上のinstance、部品の正本、業務block内の表示領域を同じpathとして扱わない。

移動先が子孫になる循環やHTML上の不正な入れ子は、最終的にcoreの文書操作が拒否する。ツリーの展開・選択はキーボードでも操作できる。

## レイアウト・レスポンシブ・モーション

レイアウトは共通のstyle宣言として扱う。横並びやGridの挿入プリセットも、通常の要素とstyleへ展開する。レスポンシブは基本宣言と幅の段の上書きを正本とし、現在表示している幅と、変更対象の段を区別する。

モーションは通常状態、hover/focus/activeの条件スタイル、遷移、登場を組み合わせる。プリセットは検証可能な宣言であり、サイト固有の実行コードを必要としない。複数項目をまとめて適用・解除する操作は1回のundoで戻せるようにする。対象外の個別styleと幅ごとの調整は保持する。

編集時の停止と公開プレビューの再生を区別し、reduced-motion、hover非対応端末、view-timeline非対応端末では内容と操作が残る。アニメーションを再生するために初期HTMLから本文を消さない。

## 読込とキャンバス

文書、サイト設定、部品、素材はそれぞれ取得結果を持つ。任意機能が失敗した場合も、文書単体で正しく検証・描画できるなら編集を開始できる。文書が参照するサイト共通定義が取得できない場合は、定義を捨てて見た目を変えず、取得失敗を示して手元の編集を保つ。別targetの遅い応答を現在の文書へ採用しない。

ページのCSS幅と、制作画面内での表示倍率は別の値とする。1280pxのページを縮小して全体表示しても、breakpointや保存される寸法は1280pxの文書として扱う。選択、ドラッグ、resize、直接文字編集の座標系を一致させる。

## 接続事例と拡張の確認

Studio shellはtrusted integrationの登録内容から編集画面を解決する。各integrationが、対象project/site、対応環境、backend、公開domain、localeと機能を定義する。登録されていない対象は閉じる。新しいsiteを扱うためにcoreへサイト名の分岐を追加しない。

鎌倉のCMS・フォーム・予約と、Experienceの体験・提供者・予約情報は、それぞれのhostが所有する。Studioの権限確認、対象を限定した署名付きbackend、公開先の検証は保持する。未接続の機能を利用可能なダミー操作にしない。

第3の架空サイトで、独自の挿入・モーション定義と登録block・共通部品を使い、挿入 → 階層移動 → 配置・動き → undo/redo → 保存 → 再読込 → SSR/CSS描画までを確認する。この事例の追加でcore/editorへサイト固有条件を加える必要があれば、拡張契約の不足として修正する。

## 互換性と実装順

今回の制作定義は、現在のwire schemaで表現できるノードとstyleへ展開する。将来、保存文書に新しいノード種別や表現を加える場合は、schemaの版、backendと公開rendererの対応、移行とロールバックを先に定義する。任意fieldの追加だけで古い厳格validatorと互換とみなさない。
